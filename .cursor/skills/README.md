# Weo0o0-Note UI/UX 스킬 가이드 (비전공자용)

이 문서는 **코딩을 전공하지 않은 사람도** “지금 블로그에 붙어 있는 스킬이 뭐고, 언제 시키면 되는지”를 같은 양식으로 이해하도록 만든 설명서입니다.

스킬은 프로그램이 아닙니다. **AI에게 주는 업무 매뉴얼**에 가깝습니다.  
요리로 치면 칼이 코드이고, 스킬은 “한식 레시피 / 위생 점검표 / 플레이팅 가이드”입니다. 같은 재료(이 블로그)라도 어떤 레시피를 펼치느냐에 따라 결과가 달라집니다.

이 사이트는 **Jekyll 블로그**입니다. 버튼을 눌러 움직이는 앱(React 같은 것)이 아니라, 글·목록·검색 페이지가 있는 **글 중심 웹사이트**입니다. 그래서 앱용 스킬은 쓰지 않습니다.

---

## 한 장으로 보는 역할

집을 고친다고 생각하면 역할이 나뉩니다.

| 순서 | 스킬 | 집 고치기 비유 | 한 줄 |
| --- | --- | --- | --- |
| 0 | weo0o0-jekyll-ui | 이 집의 설계도와 금지 사항 | 우리 블로그 전용 규칙 |
| 1 | impeccable | 인테리어 디렉터가 집을 둘러봄 | 뭐가 촌하고 뭐가 좋은지 평가 |
| 2 | web-design-guidelines | 건축 법규·소방 점검 | 기본 규칙 위반을 찾음 |
| 3 | frontend-design | 콘셉트 보드(색·글씨·분위기) | “이런 느낌으로 가자”를 정함 |
| 4 | web-design-engineer | 실제 시공 | 화면을 만듦 |
| 5 | check-fix-accessibility | 휠체어 경사로·점자 안내 | 누구나 쓰게 고침 |
| 6 | effective-ui-design | 자·수평기·간격 규칙 | 보기 좋고 읽기 쉽게 맞춤 |
| 7 | extract-design-system | 페인트 코드·타일 규격 뽑기 | 색·글씨 크기를 목록으로 정리 |

추천 순서: **우리 규칙 → 둘러보기(평가) → 법규 점검 → 콘셉트 → 시공 → 접근성 → 간격·대비 다듬기**.  
색 목록만 필요할 때는 `extract-design-system`만 단독으로 써도 됩니다.

## 작성된 스킬 카드

각 카드는 위 템플릿과 **같은 항목**입니다. 처음엔 **쉬운 별명**과 **말해 보기**만 읽어도 됩니다.

---

### 스킬 이름: weo0o0-jekyll-ui

- 쉬운 별명: 우리 집 설명서
- 한 줄 설명: “이 블로그는 이런 집이고, 저쪽 공구(React 등)는 쓰지 마라”고 AI에게 알려 주는 메모입니다.
- 왜 필요한가?: 없으면 AI가 다른 종류의 사이트(앱, 쇼핑몰)처럼 고치려다 블로그가 깨질 수 있습니다.
- 언제 시키나?:
  - “우리 블로그 규칙 먼저 읽고 고쳐줘”
  - “테마 파일을 함부로 고치지 말고 덮어쓰는 방식으로 해줘”
- 이 블로그에서 하는 일: 색·글꼴은 `assets/css/main.scss`와 `_sass/_weo0o0-overrides.scss`만 건드리고, 테마 원본 폴더는 늘리지 않게 안내합니다.
- 하지 않는 일: 예쁜 화면을 직접 그리지는 않습니다. **길 안내**만 합니다.
- 비유: 아파트 관리실에 붙어 있는 “이 단지는 페인트 이 색, 베란다는 개조 금지” 안내문.
- 말해 보기: `weo0o0-jekyll-ui 규칙 지키고 홈 화면만 다듬어 줘.`

---

### 스킬 이름: impeccable

- 쉬운 별명: 인테리어 디렉터
- 한 줄 설명: 페이지를 보고 “어디가 눈에 안 들어오는지, 촌스러운지, 너무 시끄러운지”를 평가한 뒤 다듬는 전문가입니다.
- 왜 필요한가?: 색만 바꾸면 해결될 일과, 배치를 바꿔야 할 일을 구분하지 못하면 손만 많이 가고 사이트는 그대로입니다.
- 언제 시키나?:
  - “홈이 밋밋해. 왜 그런지 평가해 줘”
  - “404 페이지 느낌 어떤지 봐 줘”
  - “너무 화려하면 오히려 조용하게 만들어 줘”
- 이 블로그에서 하는 일: 홈, 글 본문, 검색, 404처럼 **이미 있는 화면**을 먼저 비평합니다.
- 하지 않는 일: 서버나 글 내용을 새로 쓰지 않습니다. 로그인·결제 같은 앱 기능도 대상이 아닙니다.
- 비유: 인테리어 방송에서 디자이너가 현관에 서서 “소파가 TV를 가리고 있어요”라고 짚는 장면.
- 말해 보기: `impeccable으로 홈과 404를 critique한 다음, 큰 문제부터 알려 줘.`

---

### 스킬 이름: web-design-guidelines

- 쉬운 별명: 안전·품질 점검표
- 한 줄 설명: “버튼에 초점이 보이느냐, 그림에 설명이 있느냐, 어두운 화면에 맞는 설정이냐”처럼 **웹의 기본 규칙**을 대조합니다.
- 왜 필요한가?: 예쁜데 키보드로 메뉴를 못 열거나, 링크인지 알기 어려우면 실제 방문자가 막힙니다.
- 언제 시키나?:
  - “우리 사이트 UX 점검해 줘”
  - “접근성이랑 기본 규칙 위주로 리뷰해 줘”
- 이 블로그에서 하는 일: `_layouts/`, `_includes/`, `_pages/`처럼 **뼈대 파일**을 규칙 목록과 맞춰 봅니다.
- 하지 않는 일: 새로운 디자인을 제안하는 자리가 아닙니다. **위반 사항을 찾는 자리**입니다.
- 비유: 식당 개업 전 보건소 점검. 맛(예쁨)이 아니라 싱크대·소화기부터 봅니다.
- 말해 보기: `web-design-guidelines로 헤더, 검색, 404를 점검하고 파일 위치랑 같이 알려 줘.`

---

### 스킬 이름: frontend-design

- 쉬운 별명: 콘셉트 디자이너
- 한 줄 설명: 색, 글씨, 여백의 **분위기**를 먼저 정해서 “어디서나 볼 법한 AI 기본 디자인”이 나오지 않게 합니다.
- 왜 필요한가?: 콘셉트 없이 고치면 보라색 그라데이션, 똑같은 카드 격자처럼 **남들과 같은 얼굴**이 되기 쉽습니다.
- 언제 시키나?:
  - “블로그 분위기를 더 또렷하게 하고 싶어”
  - “글씨랑 색 조합을 우리 블로그답게 정해 줘”
- 이 블로그에서 하는 일: 이미 쓰는 **어두운 배경 + 청록 포인트 + 고운바탕/고운돋움**을 지키면서, 그 안에서만 개성을 키웁니다.
- 하지 않는 일: 평가(impeccable)나 법규 점검(guidelines)을 건너뛰고 처음부터 간판을 바꾸라는 뜻이 아닙니다.
- 비유: 옷 사기 전에 “단정한 겨울 출근룩”인지 “여름 피크닉”인지 무드를 정하는 일.
- 말해 보기: `frontend-design으로 콘셉트를 짧게 정한 뒤, 테마 원본은 건드리지 말고 덮어쓰기만 해 줘.`

---

### 스킬 이름: web-design-engineer

- 쉬운 별명: 시공 팀
- 한 줄 설명: 정해진 콘셉트를 **실제 웹 페이지**로 만듭니다. 이 프로젝트에서는 HTML/CSS 쪽 결과물을 블로그 구조에 맞게 옮깁니다.
- 왜 필요한가?: 아이디어만 있고 화면이 안 바뀌면 방문자는 차이를 못 느낍니다.
- 언제 시키나?:
  - “이 시안으로 404를 실제로 고쳐 줘”
  - “공지 배너 같은 새 조각을 만들어 줘”
- 이 블로그에서 하는 일: 레이아웃·부분 템플릿(`_layouts`, `_includes`)과 스타일 덮어쓰기에 반영합니다.
- 하지 않는 일: 이 저장소를 React 앱으로 바꾸거나, Tailwind/shadcn 같은 **다른 공법**을 새로 들이지 않습니다.
- 비유: 도면(콘셉트)을 보고 벽에 페인트와 몰딩을 실제로 시공하는 팀.
- 말해 보기: `web-design-engineer로 404만 시공해 줘. Jekyll 구조를 유지해.`

---

### 스킬 이름: check-fix-accessibility

- 쉬운 별명: 누구나 쓰기 담당
- 한 줄 설명: 눈이 잘 안 보이거나, 마우스를 못 쓰거나, 화면 낭독기를 쓰는 사람도 **글을 읽고 메뉴를 누를 수 있는지** 보고 고칩니다.
- 왜 필요한가?: 색만 예쁜 버튼은, 대비가 낮으면 읽기 어렵고, 키보드로는 어디를 누르는지도 모릅니다.
- 언제 시키나?:
  - “접근성 맞춰 줘”
  - “키보드만으로 메뉴가 되는지 봐 줘”
  - “글자와 배경 대비 확인해 줘”
- 이 블로그에서 하는 일: 건너뛰기 링크, 검색 버튼, 404, 다크 모드 대비율을 점검합니다.
- 하지 않는 일: “디자인을 더 화려하게”가 목표가 아닙니다. **쓰는 데 막힘이 없게**가 목표입니다.
- 비유: 건물 출입구에 경사로와 점자 안내를 다는 일. 인테리어와는 다른 필수 공사입니다.
- 말해 보기: `check-fix-accessibility로 홈·404·검색을 WCAG 기준으로 점검하고 고칠 점만 알려 줘.`

---

### 스킬 이름: effective-ui-design

- 쉬운 별명: 자·수평기
- 한 줄 설명: 글자 크기, 버튼 크기, 여백, 다크 모드, “움직임 줄이기”처럼 **읽기 편한 디테일 규칙**을 적용합니다.
- 왜 필요한가?: 콘셉트는 좋은데 줄 간격이 빽빽하거나, 애니메이션이 어지러우면 오래 읽기 힘듭니다.
- 언제 시키나?:
  - “글이 답답해 보여. 간격이랑 글자 크기 다듬어 줘”
  - “다크 모드랑 움직임 줄이기도 챙겨 줘”
- 이 블로그에서 하는 일: 이미 넣어 둔 CSS 변수, 포커스 테두리, `prefers-reduced-motion` 같은 규칙을 지키며 미세 조정합니다.
- 하지 않는 일: 블로그 주제나 글 내용을 바꾸지 않습니다.
- 비유: 액자를 걸 때 줄자를 대고 1cm씩 맞추는 일.
- 말해 보기: `effective-ui-design 기준으로 본문 여백이랑 버튼 위계만 다듬어 줘.`

---

### 스킬 이름: extract-design-system

- 쉬운 별명: 색·글씨 표본 채집
- 한 줄 설명: 사이트에 쓰인 색, 글꼴, 간격 같은 **반복되는 값**을 목록으로 뽑습니다. 나중에 같은 색을 헤매지 않게 합니다.
- 왜 필요한가?: 색이 파일마다 조금씩 다르면, 고칠 때마다 “이 회색이 그 회색인지” 헷갈립니다.
- 언제 시키나?:
  - “우리 블로그 색이랑 글씨 규칙을 표로 뽑아 줘”
  - “다른 사이트 느낌을 참고하되, 값만 목록으로 가져와 줘”
- 이 블로그에서 하는 일: `_sass`와 라이브 페이지에서 토큰을 읽어, 테마 원본을 복제하지 않고 덮어쓰기 파일에 정리합니다.
- 하지 않는 일: 화면을 화려하게 다시 그리는 스킬이 아닙니다. **재료 명세서**를 만드는 스킬입니다.
- 비유: 옷장에서 자주 입는 옷의 색 번호와 치수를 수첩에 적는 일.
- 말해 보기: `extract-design-system으로 지금 다크 스킨 색·서체·간격을 목록으로만 정리해 줘.`

## 스킬이 참고하는 재료 (Git 저장소)

스킬이 “어떻게 고칠지”를 알려 주면, 아래는 **페인트·서체·검사 도구**입니다.

| 쉬운 이름 | 하는 일 | 비유 |
| --- | --- | --- |
| Catppuccin Mocha | 어두운 배경·글자색 표본 | 야간 모드용 물감 세트 |
| Gowun Batang / Gowun Dodum | 본문 글씨 / 메뉴·버튼 글씨 | 본문용 만년필, 간판용 사인펜 |
| Pretendard | 메뉴 글씨가 없을 때 대신 쓰는 글씨 | 예비 볼펜 |
| pa11y + axe | 페이지가 쓰기 불편한지 자동으로 두드려 봄 | 출입구가 막혔는지 확인하는 점검 앱 |

로컬에서 사이트를 켠 뒤 검사하려면, 터미널에서 `npm run pa11y:home` 또는 `npm run pa11y:ci`를 쓰면 됩니다. (Jekyll이 `4000` 포트에서 실행 중이어야 합니다.)

## 채팅창에 이렇게 말하면 됩니다

상황별로 **그대로 복사**해도 됩니다.

1. 어디가 문제인지부터:  
   `우리 집 설명서 읽고, impeccable으로 홈이랑 404를 평가해 줘.`
2. 기본 규칙만:  
   `web-design-guidelines로 헤더·검색·404만 점검해 줘.`
3. 분위기만 정하기:  
   `frontend-design으로 콘셉트만 짧게. 코드는 아직 바꾸지 마.`
4. 정해진 대로 고치기:  
   `시공은 web-design-engineer로, 테마 원본 폴더는 건드리지 마.`
5. 누구나 쓰이게:  
   `check-fix-accessibility로 키보드랑 대비만 봐 줘.`
6. 색 목록만:  
   `extract-design-system으로 지금 쓰는 색과 글씨만 표로 뽑아 줘.`

한 번에 모든 스킬을 부르지 않는 편이 낫습니다. **한 가지 목적에 스킬 하나**가 비전공자에게도, AI에게도 덜 헷갈립니다.

## 비전공자가 자주 하는 오해

- “스킬을 설치하면 블로그가 자동으로 예뻐지나?”  
  → 아닙니다. **채팅에서 일을 시켜야** 움직입니다.
- “스킬이 많을수록 좋은가?”  
  → 아닙니다. 이 블로그와 안 맞는 앱용 스킬은 일부러 빼 두었습니다.
- “스킬 이름이 영어로 어려워 보여요.”  
  → 카드의 **쉬운 별명**만 기억해도 됩니다. 채팅에는 영어 이름을 붙여 주면 AI가 매뉴얼을 정확히 찾습니다.
